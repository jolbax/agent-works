# Loop prompt templates

Project-agnostic prompts for the spec-driven loop described in [docs/dev-loop.md](../../docs/dev-loop.md). Copy them unchanged. Models and effort levels are left to the operator's defaults (`--model`, `--effort`).

**Placeholders.** `<name>` is a launch-time placeholder, filled when the prompt is built. `{name}` is a runtime value the worker resolves itself while running (for example `{N}` its PR number, `{sha}` the head the operator approves, `{merge-commit}` the merge commit `loop-merge.sh` printed, `{round}` the fix round). Never replace a `{name}` by hand.

**Building a prompt.** Run from the repository root:

```bash
bash scripts/loop-prompt.sh .agents/loop/<template>.md <prompt-file> key=value...
```

It writes the text after the template's first `---` line, with each `<key>` replaced literally by its value, to `<prompt-file>`, and keeps every `{name}`. It exits 1 naming each launch-time placeholder left unfilled (nothing is written), and 2 on usage errors. For a template with "Intake:" lines give exactly one of `issue-number` and `brief`; the other Intake line is dropped.

| Template | Step | Documented keys (all also take `owner`, `repo`, `change-name`) | Launched with |
| --- | --- | --- | --- |

**Launching.** The normal way is the `sdd-loop` skill (`/sdd-loop start|implement|judge|amend|archive|status` in an agent in the main worktree), which runs `scripts/loop-start.sh`: it derives every value in the table from GitHub, builds the prompt with `loop-prompt.sh` and launches with `loop-launch.sh`; `--dry-run` prints the prompt path and launch command only. The manual commands in the table are the fallback. `scripts/loop-launch.sh <name> <agent> <prompt-file> [worktree-create args]` confirms the agent started working and resends the prompt once if not (exit non-zero if that fails too). Every worker except the judge reports its state on its Orca worktree with `scripts/loop-status.sh`.

**Hand-off.** A worker that stops for the operator runs `bash scripts/loop-await.sh {N} approve|judge` instead of building the line. The helper waits up to 60 s until GitHub shows the head the worker pushed (exit 1 without touching Orca if not), sets `in-review` with the PR linked and prints the line. Propose, amend and archive use `approve` (`PR #<N> at <sha7>: review, then type: approve <sha7>`); apply and fix use `judge` (`PR #<N> at <sha7>: ready for the judge (launch it, then wait for its verdict)`). Only the judge's verdict line asks for approval of an implementation PR; the operator then answers in the builder's terminal, and the worker merges with `scripts/loop-merge.sh <N> <sha>`.

**Cleanup.** After a change's archive PR merges, ask the skill agent to clean up (`/sdd-loop cleanup`). It runs `bash scripts/loop-start.sh cleanup --dry-run` first and shows the list (`remove` or `keep: <first failing rule>` per worktree), and runs `bash scripts/loop-start.sh cleanup` only after the operator types `yes, clean up` in that agent's terminal. A worktree is removed only if, in this order: it is neither the main worktree nor the one the script runs in; its status is `completed`; its name is `<change>`, `<change>-impl`, `<change>-judge`, `<change>-judge-<N>`, `<change>-amend`, `<change>-amend-<N>` or `<change>-archive` of a change directory on `origin/<default branch>`; its HEAD is an ancestor of `origin/<default branch>`; its linked PR, if any, is merged or closed; it has no uncommitted or untracked files. Removal uses `orca-ide worktree rm --worktree path:<path> --json`, never `--force`, and reports per worktree whether the local branch was deleted or kept and which terminals remain. The first failed removal stops the run with exit 8. Remote branches are never deleted; enable the repository's delete-branch-on-merge setting for that.

**Change requests.** Any message other than the exact `approve <sha>` (and `fix` for a builder) is a change request: the propose, amend, apply or archive worker makes the changes within its MUST-NOT limits, pushes, and runs `loop-await.sh` again with its mode.

**Fix rounds.** The round is the count of comments on the PR that begin with `Verdict: BLOCKING`. Above 2, the builder does not fix and sets `in-review` with "two fix rounds used; operator decides on GitHub".

**Settling a finding about the approved change.** When a judge finding concerns the approved change's own wording rather than the implementation, the operator decides and records the decision with `/sdd-loop amend <change>: <text>`. The amend worker edits only `openspec/changes/<change>/`, never a checkbox state, and opens a draft spec-only PR titled `amend: <change>` with `Kind: spec` that quotes the operator's text. The operator reviews it and types `approve <sha7>` in the amend worker's terminal; after the merge, the operator launches a re-judge, which reads the amended change from the default branch. A judge does not accept an operator decision quoted in a PR body, PR comment, issue or another agent's output; only the merged change on the default branch is the operator's decision. An amendment is not a fix round. If the implementation PR then conflicts on `tasks.md`, the operator asks the builder, as a change request, to merge the default branch into its branch.

**Requirement length.** Propose keeps every requirement text under 500 characters and checks it with `bash scripts/spec-length.sh openspec/changes/<change-name>` (`openspec validate` does not measure MODIFIED requirements). If strict validation fails after the archive sync on a requirement over 500 characters, the archive worker shortens it without changing its meaning, inside `openspec/`, and records it in the PR description.

Note: Orca marks a worktree unread when its agent finishes a turn, which can override the read mark that `loop-status.sh` sets.

Manual fallback: confirm with `orca-ide terminal read --terminal <handle> --screen`; if the agent sits at an empty input, resend the prompt with `orca-ide terminal send --terminal <handle> --text … --enter --wait-submit 20`.
